# Blockbench producer-integration protocol

## Scope

This protocol defines the valid local integration boundary for content authored
with Blockbench plugins. The first pinned producer is Animated Java 1.10.2 in
Blockbench 5.1.4, exporting its upstream Minecraft 1.20.4 minimal armor-stand
blueprint.

A valid result crosses two independently named gates:

1. the real Blockbench desktop host loads the official plugin and exports the
   blueprint through the plugin's public export action;
2. Minosoft consumes the byte-exact captured output through its normal asset,
   model, data-pack, entity, and content-generation paths.

Neither gate substitutes for the other. Directly invoking an extracted
compiler module is not Blockbench integration, and consuming an old fixture
does not prove that a newer producer still exports it.

## Accepted producer gate

The producer gate is valid when all of these conditions hold:

- the Blockbench application archive, plugin release file, and source blueprint
  are pinned by identity and SHA-256; the plugin source is pinned by tag and
  commit, and the Minecraft target is exact;
- Blockbench uses a new isolated user-data directory with updates disabled, so
  installed plugins and prior local state cannot satisfy the test accidentally;
- the official desktop plugin is loaded by Blockbench with its release
  filename unchanged;
- Blockbench opens the source blueprint through its normal project codec;
- the harness invokes the same public operation used by the export UI:

  ```javascript
  await AnimatedJava.exportProject({forceSave: false, debugMode: false})
  ```

- resource-pack and data-pack destinations are empty absolute temporary
  directories;
- the harness treats a plugin load failure, page exception, rejected export,
  unexpected dialog, timeout, or Blockbench process exit as failure;
- no generated file is normalized, pruned, or hand-edited;
- provenance, file counts, per-file hashes, and the sorted output-manifest hash
  are recorded before the temporary producer process is stopped.

Chromium DevTools Protocol is an acceptable local automation transport for the
desktop Electron application. It may observe readiness, exceptions, and invoke
the public export operation, but it must not bypass plugin registration,
project decoding, or either compiler.

The exact producer identities and the successful captured result live in
[Animated Java Blockbench export evidence](../evidence/2026-07-24-animated-java-blockbench-export.md).
Third-party applications, plugins, source checkouts, caches, and scratch output
remain outside the repository.

## Captured-output contract

The accepted output is stored below:

```text
src/integration-test/resources/content_fidelity/
└── animated_java-1.10.2-export/
    ├── fixture.json
    ├── resources/
    └── datapacks/
```

`fixture.json` is producer provenance and is excluded from the generated-output
manifest. The manifest is the SHA-256 of sorted lines:

```text
<file-sha256>  <relative-path>\n
```

for every regular file below `resources/` and `datapacks/`. A producer rerun is
accepted as identical only when the file counts and manifest hash match. If
they differ, preserve both identities long enough to review the semantic diff;
do not silently replace the fixture.

## Automated Minosoft gate

Run the captured output through Minosoft with Java 25:

```sh
./gradlew integrationTest \
  --tests de.bixilon.minosoft.local.datapack.AnimatedJavaExportFixtureTest
```

The gate verifies:

- the complete output manifest;
- separate resource-pack and data-pack mounting;
- all seven generated models and the source texture;
- generated load, summon, animation, and removal functions;
- the item-display root and seven passenger nodes using custom model data
  `2..8`;
- retained entity identity and advancing animation across eight content
  replacements;
- rejected-generation rollback, recovery, and once-only CPU-generation
  cleanup.

This test is deterministic and headless. It is suitable for ordinary local and
CI integration testing, but it intentionally consumes the checked-in fixture
instead of launching a desktop application.

## Companion CEM/ETF consumer gate

Blockbench can author content for several runtime formats, but a renderer
integration fixture and a producer integration fixture answer different
questions. The checked
`acceptance/scenarios/emf-etf-zombie-render-reference.json` scene is the first
bounded CEM/ETF consumer gate:

```sh
./play.sh scenario run \
  acceptance/scenarios/emf-etf-zombie-render-reference.json \
  --trajectory emf-etf-render-reference --json
```

It validates Minosoft's normal resource/data-pack mounting, ETF property
selection, EMF expression context, native zombie composition, fixed local
summon/removal, production content reload, exact pixels, and typed OpenGL
rollback. The staged EMF `3.0.17` bytecode establishes `rule_index` as the
public CEM variable; ETF's `textureRule` spelling belongs to ETF property
conditions and is not accepted as an EMF alias.

This fixture is intentionally labeled `producer: Minosoft acceptance`. It must
not be used as evidence that a Blockbench CEM exporter works. To add that
producer claim, pin and automate the exact Blockbench host, CEM/OptiFine plugin,
source project, target version, export action/settings, and byte manifest using
the producer gate at the start of this protocol. Keep both fixtures if the
producer capture broadens the accepted surface.

The full evidence and remaining gates are recorded in
[EMF/ETF render reference evidence](../evidence/2026-07-26-emf-etf-render-reference.md).

## When to recapture

Recapture under a new independently identified fixture when changing any
producer input:

- Blockbench version or platform artifact;
- plugin version, release artifact, source commit, or release filename;
- source blueprint;
- Minecraft target version;
- plugin export settings that affect output.

A new fixture should broaden the accepted surface rather than overwrite the
existing producer identity. Keep the old gate until the supported-version
policy intentionally retires it.

## Repeatable local real-OpenGL gate

The `content-fidelity` manifest declares the exact export in `fixtures.tsv`.
`Play` validates its manifest/counts, stages it transactionally in the
out-of-source modpack store, preserves user asset entries, and mounts its
resource and data roots as ordinary session packs. Launch a fixed void world:

```sh
MINOSOFT_JAVA_HOME=/opt/homebrew/opt/openjdk@25 \
./play.sh dev client --local-world --world-generator void \
  --modpack content-fidelity \
  --trajectory animated-java-render-reference
```

Summon the export through the mounted production `SessionDataPackRuntime` and
set an explicit player camera:

```sh
./play.sh debug request content.execute-local \
  '{"function":"aj:armor_stand_minimal/summon","arguments":{"args":"{}"},"origin":{"x":0.5,"y":20.0,"z":0.5,"yaw":0.0,"pitch":0.0},"camera":{"x":0.5,"y":19.5,"z":3.5,"yaw":180.0,"pitch":0.0}}' \
  --role client --trajectory animated-java-render-reference --json

./play.sh debug state client.entities \
  --role client --trajectory animated-java-render-reference --json

./play.sh debug visual capture /tmp/animated-java-default.png \
  --role client --trajectory animated-java-render-reference --json

./play.sh debug request render.substrate '{}' \
  --role client --trajectory animated-java-render-reference --json
```

The entity sample must expose one generated root with seven passengers and
item-display custom-model-data values `2..8`. Exercise the production content
transaction, capture again, and remove the generated hierarchy:

```sh
./play.sh debug request render.reload-content '{}' \
  --role client --trajectory animated-java-render-reference --json

./play.sh debug request content.execute-local \
  '{"function":"animated_java:global/remove/everything","arguments":{},"origin":{"x":0.5,"y":20.0,"z":0.5,"yaw":0.0,"pitch":0.0},"camera":{"x":0.5,"y":19.5,"z":3.5,"yaw":180.0,"pitch":0.0}}' \
  --role client --trajectory animated-java-render-reference --json
```

`content.execute-local` is deliberately local-world-only. It accepts one
bounded resource location, bounded string macro arguments, finite bounded
origin/camera coordinates, and no arbitrary code or remote-server mutation.
The operation uses the normal session runtime and render queue.

The checked scenario is:

```sh
./play.sh scenario run \
  acceptance/scenarios/animated-java-render-reference.json \
  --trajectory animated-java-render-reference --json
```

It first clears transient GUI overlays and disables the HUD, entity hitboxes,
and moving clouds, requires the `3456x1910` framebuffer, then crops
`[1100,900,550,550]`. The checked default pose and static `walk` frame 10 both
use zero pixel, ratio, and mean-error tolerance. The walk frame is compared
again after a production content reload. The baseline README records the
platform identity and hashes.

On 2026-07-25 the scenario passed twice on the documented Apple M4 Max target,
including a run that deliberately began with the pause menu open. Ten earlier
default-pose captures were identical, and four content generations retained
the mounted functions. Summon added a stable 42 live model objects (28 buffers
and 14 vertex arrays); removal returned to the warmed baseline family without
cumulative growth.

The transactional rejection lane is:

```sh
./play.sh scenario run \
  acceptance/scenarios/animated-java-rejected-reload.json \
  --trajectory animated-java-rejected-reload --json
```

It rejects once after candidate upload and once after texture/model lookup
publication. Both operations execute on the render thread through the normal
content transaction. On 2026-07-25 each allocated and retired 16 buffers plus
eight vertex arrays, reported zero live delta for all eight OpenGL resource
types, retained generation 1, and preserved the exact walk crop. The mounted
remove/summon functions remained callable and an accepted recovery published
generation 3; the skipped ID is the intentionally rejected publication
candidate.

Run `animated-java-render-cleanup.json` with
`--debug-gpu-memory-leaks` for the explicit disposal lane. It summons and
removes the generated hierarchy, moves the camera 512 blocks and back to
replace cloud arrays, and verifies only the local player remains. Two forced
collections after that sequence emitted no new finalizer warning. This run
also found and fixed an independent cloud-grid ownership leak:
`CloudArray.unload` now releases its mesh, shifts unload only the outgoing
edge, pending retired layers drain once, and renderer shutdown releases active
and pending layers.

These are platform-qualified production-path references, not a universal GPU
parity claim. Other drivers, a remote 1.20.4 server, glowing outline pixels,
and broader blueprints remain. Do not weaken or rewrite the generated fixture
if any gate regresses.
