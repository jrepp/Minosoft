# Fabric hook backlog

This backlog contains hook families that cannot yet satisfy Minosoft's ownership,
thread-affinity, rollback, or unload invariants. Do not substitute observation-only
callbacks and label them as complete. When a prerequisite lands, implement the
hook at the named authoritative boundary and move it into dated evidence.

| Hook family | Blocking evidence | Required host change | Acceptance gate |
| --- | --- | --- | --- |
| Atomic shader/texture replacement | Program and shader-pipeline replacement now preserve the active generation on candidate failure. Typed driver-side counts exist, but texture managers still mutate live arrays and repeated replacement has no accepted steady-state baseline. | Extend the generation/swap/retirement contract in the [render-substrate target](render-substrate.md) to texture arrays and physical layouts. | Invalid replacement preserves prior visual/program/texture IDs; repeated valid swaps return driver-side GPU counts to baseline. |
| Registry epochs and content reload | `FabricSessionContentBridge` adds directly to session registries; registries expose no transactional remove/freeze/rollback or palette migration. Existing chunks may retain old state IDs. | Immutable registry generation, stable identity remap, world/chunk migration policy, and atomic session publication. | Failed generation keeps the old registry/world readable; valid generation migrates or explicitly rejects old states without aliasing IDs. |
| General data reload (recipes, tags, loot, worldgen) | There is initial registry/tag loading and asset reload, but no unified prepared data-generation object or rollback boundary. | Candidate data generation covering tags/recipes/loot/worldgen with dependency ordering and atomic publication. | Reload ordering is deterministic, failure preserves the old generation, and consumers never see mixed generations. |
| Model-loader plugins | `ModelLoader`, `BlockLoader`, and `ItemLoader` own concrete load/bake maps with no resolver chain or callback-specific removal. | Owner-scoped resolver registry, candidate bake generation, cache invalidation, and render-thread disposal. | Custom model resolves and bakes; unregister/reload removes it and releases meshes/textures without invalidating vanilla models. |
| Custom block-entity and special-item renderers | Vanilla special renderers are hard-coded in `DefaultBlockEntityModels`; the generalized `builtin/entity` path can keep unknown items visible, but cannot reproduce mod geometry, animation, NBT variants, or lifecycle-safe unload. | Owner-scoped block-entity and item-render factory registries, explicit render-thread installation/removal handles, model-generation ownership, and section invalidation when ownership changes. | A source-native mod hot-adds a crafted special-render block and matching item, reloads its geometry/texture, then unloads with affected sections remeshed and GPU/resource counts returned to baseline. |
| Render-pass registration | The canonical production graph now has stable IDs, semantics, dependencies, and immutable generations. Scene assembly still lacks a general owner-scoped hot-add/remove API for external passes. | Add an owner-scoped contribution registry that rebuilds the [render-substrate target](render-substrate.md) generation at the render safe point. | A pass hot-adds/removes across active/future contexts; draw order is stable and old renderer/GPU resources are collectible. |
| Terrain-backend replacement | Sodium is the exclusive graph-visible provider while active, with a frame-pinned generation and duplicate-submission checks, but its backend delegates Minosoft's scheduling, meshing, upload, visibility, and batching core. | Put the exact pinned Sodium algorithms behind the semantic terrain ABI defined by the [render-substrate target](render-substrate.md), then meet its performance gate. | With Sodium active it is the sole behavioral terrain owner; built-in and Sodium profiles pass base, unload, performance, and multi-version gates without duplicate submissions. |
| Shader-pipeline replacement | Iris transactionally executes a bounded project reference pack with terrain, shadow, target, and final-composite programs. It has not passed an independent pinned shader pack or the broader program/uniform/sampler contract. | Extend the typed shader provider in the [render-substrate target](render-substrate.md) using an independent real-world pack, with explicit rejection for unsupported semantics. | A real pinned pack executes all required views and composites, invalid reload preserves the active generation, and Iris composes with Sodium terrain. |
| Block-entity lifecycle | `BlockEntityDataProvider.set` can run while the chunk lock is held; `setData`/`clear` are not lifecycle-aware. Calling arbitrary mod code there can deadlock or observe a half-applied batch. | Post-commit block-entity delta batch emitted after chunk locks, including load/replace/clear causes. | Single and bulk changes publish exact previous/current entities after commit, with no callback under world/chunk locks. |
| Persistent mod state | `WorldStorage` only has `load(World)` and the local implementations expose no namespaced durable read/write, schema, transaction, or migration contract. | Trajectory-scoped namespaced store with atomic files, quotas, codec/version metadata, and explicit session/world ownership. | State survives process reload, invalid/migrating data is recoverable, one mod cannot read/write another namespace, and unload closes all handles. |
| General container transactions and slot policy | Owned container-screen decorators now exist, and the exact Inventory Management adapter can delegate sort/transfer/stack to its pinned upstream Fabric server handlers. That path has no general capability handshake, revisioned Minosoft transaction plan, stale-state rollback, or owner-ordered slot interception for locking and automatic replacement. | Normalized owner-scoped slot-input policy, a candidate transaction plan with revision validation/rollback, and an explicit client/server capability handshake independent of one upstream mod version. | A source-native canary hot-adds/removes input policy; native sort/transfer plans preserve item counts across stale-revision rejection; unsupported servers disable actions; unload removes policy, bindings, config, and packet registrations from current/future screens. |
| Dedicated-server lifecycle/ticks/payload/commands in the Minosoft host | Minosoft is a client; `LocalConnection` is an in-process authority adapter, not a Fabric dedicated server runtime. The test server already runs real Fabric API and the debug bridge uses its standard server events. | Define a separate Minosoft server product/runtime before creating source-native server APIs. | Multi-world server start/stop/ticks, commands, payloads, persistence, and mod unload are owned and independently tested. |
| Fabric binary API adapters | Source-native contracts use Minosoft types; Mojang/Fabric callback, registry, networking, rendering, and loader classes are absent from the client classpath. | Per-module translation facade or maintained compatibility module with exact version fixtures. | A mod compiled against each advertised Fabric API module links unchanged and passes behavior tests; unimplemented modules fail preflight. |
| Mixin/access-widener replacements | Upstream injections target Mojang class layouts and private members that do not exist in Minosoft. | Review each requested behavior and add a stable domain hook only when it has a source-native owner and cleanup boundary. | Each adapter names the replaced behavior and proves parity; unknown injections stay blocked by default. |

Implemented source-native families are cataloged by `FabricFunctionalityCatalog`
and summarized in the [mod-workflow map](../areas/08-modding.md). The backlog is
ordered by prerequisite ownership work, not by upstream module name.
